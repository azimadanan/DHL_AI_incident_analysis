## Commands

### Backend
```bash
cd backend
npm start          # start server on port 3000
```

### Frontend
```bash
cd frontend
npm run dev        # start Vite dev server (proxies /api → localhost:3000)
npm run build      # production build
```

Both must run simultaneously for the app to work. Backend must start first.

Copy `.env` in `backend/` and set:
```

DB_PORT=3306
DB_USER=root
DB_PASSWORD=
DB_NAME=dhl_incidents
JWT_SECRET=your_secret
```

## Architecture

### Overview
Full-stack incident management system for DHL. React frontend + Express backend + MySQL. UiPath RPA reads files from Google Drive and posts to the backend API to auto-create incidents.

```
frontend (Vite + React)  →  /api/*  →  backend (Express + MySQL)
                                              ↑
                              UiPath RPA (POST /api/ingest)
```

### Backend (`backend/`)

**`server.js`** — all routes in one file:
- `POST /api/login` — JWT auth
- `GET/POST /api/incidents` — list + create (auth required)
- `PATCH /api/incidents/:id/status` — status update + writes to `incident_history` table
- `GET /api/incidents/:id/history` — audit trail
- `POST /api/ingest` — **no auth required** — UiPath calls this to create incidents
- `GET /api/reports` — aggregated stats (by status, category, priority)
- `GET /api/export/:format` — admin-only, exports xlsx/pdf/docx
- `POST /api/upload-file` — parses pdf/docx/txt files and returns extracted text
- `GET /api/export` — no-auth JSON dump for RPA consumption

**`db.js`** — MySQL pool, auto-creates all tables and seeds default users/incidents on first run. Incident IDs start at 100001, incremented via a `meta` table key `nextId`.

**`ai.js`** — fully offline AI pipeline:
1. Tries `Xenova/distilbart-mnli-12-3` (zero-shot classification) first
2. Falls back to trigger-word scoring if model confidence < 0.35 or model fails
3. Categories: `Late Delivery`, `Damaged Parcel`, `Address Issue`, `System Error`, `Customer Complaint`
4. Priority: `High` / `Medium` / `Low` via keyword scoring
5. `isDHLRelated()` — filters non-DHL content before creating incidents
6. `generateSummary()` — returns structured HTML with extracted tracking numbers, amounts, demands, escalation flags
7. Duplicate detection: matches tracking numbers (e.g. `MY123456`, `DHL-1234`) against unresolved incidents

### Frontend (`frontend/src/`)

**Routing** (`App.jsx`):
- `/` → Dashboard
- `/submit` → SubmitIncident
- `/incidents/:id` → IncidentDetail
- `/reports` → Reports
- `/reports/category` → CategoryBreakdown
- `/settings` → Settings

**Key patterns:**
- All API calls go through `api.js` (axios instance with JWT interceptor + auto-logout on 401)
- Dashboard auto-refreshes every 10 seconds to show new RPA-created incidents
- `dangerouslySetInnerHTML` is used in IncidentDetail to render the HTML summary generated by `ai.js` — the HTML is escaped server-side in `escapeHtml()` before storage
- Inline styles throughout — no CSS framework, no separate stylesheet files
- `NavLink` uses `end` prop on `/` and `/reports` to prevent both links being active simultaneously

**Status values:** `Draft` → `Reviewed` → `Published` (versioning track) and `Open` → `In Progress` → `Resolved` (resolution track). Both tracks coexist on a single incident.

### UiPath RPA (`rpa/` + `uipath/`)

UiPath communicates with the web app via HTTP only:
- **Create incident:** `POST http://localhost:3000/api/ingest` — no token needed
- **Update status:** `PATCH http://localhost:3000/api/incidents/{id}/status` — no token needed via ingest flow

Local RPA folders (all pre-created):
```
rpa/
  incoming/            ← downloaded Drive files
  logs/                ← run logs written after each execution
  screenshots/         ← proof screenshots of created incidents
  errors/              ← error screenshots on failure
  processed_hashes.txt ← 14-day hash dedup record (format: hash|yyyy-MM-dd per line)
```

### Important Notes
- Export routes (`/api/export/:format`) are admin-only — non-admins get 403
- `ai.js` has `DEBUG = true` at the top — set to `false` to silence verbose console output in production
- The `incident_history` table logs every status change with old/new status, who changed it, and timestamp
- Tags are stored as comma-separated strings in the DB and returned as arrays via `normalizeIncident()`
